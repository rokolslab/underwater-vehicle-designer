# Базовые правила проекта

> Автоматически выявленные соглашения из текущего кода и технической спецификации. При развитии проекта обновляйте этот файл вручную.

## Именование

- Файлы: TypeScript-модули используют преимущественно `kebab-case`; сложившиеся app-файлы `appState.ts` и `projectState.ts` сохраняют `camelCase`.
- Переменные: `camelCase`.
- Функции: `camelCase`, глагольные имена для действий (`makeProfileSnapshot`, `normalizeScene3dSettings`, `buildCsv`).
- Классы, типы и интерфейсы: `PascalCase`.
- Экспортируемые физические и схемные константы: `UPPER_SNAKE_CASE` или сложившееся публичное имя, если оно уже входит в контракт.

## Структура модулей

- `src/app` отвечает за Vite entrypoint, DOM orchestration и агрегирование состояния проекта.
- `src/modules/geometry` содержит чистую геометрию, станции, сечения и общий `ProfileSnapshot`.
- `src/modules/equipment` содержит модель оборудования, операции размещения и ограничения.
- `src/modules/balance` содержит ЦТ, ЦВ, плавучесть и моменты; геометрию ЦВК здесь не размещайте.
- `src/modules/rendering` содержит Canvas 2D, Three.js и adapters координат.
- `src/modules/persistence` содержит импорт и экспорт JSON, CSV и SVG.
- `src/modules/ui` связывает typed DOM controls с состоянием, но не реализует расчетную геометрию.
- `src/shared` содержит только общие типы и небольшие независимые helpers.
- Canvas, SVG, CSV, таблицы, метрики и 3D должны использовать общий `ProfileSnapshot`, а не пересчитывать геометрию независимо.

## Обработка ошибок

- Пользовательский числовой ввод нормализуйте через явные функции валидации и fallback-значения.
- Расчетные функции не должны напрямую читать DOM или изменять UI.
- Для невозможной геометрии возвращайте структурированный результат с причиной ошибки, а не скрыто исправляйте состояние.
- Ограничения размещения оборудования должны быть проверяемыми отдельно от визуального слоя.
- Импортируемые данные проверяйте от `unknown` через type guards и нормализаторы; миграции схемы JSON должны быть односторонними и покрыты тестами.

## Поток управления

- Предпочитайте плоский читаемый поток с guard clauses и ранними `return`; выделяйте helper только когда он упрощает самостоятельную операцию.
- Не добавляйте compatibility-код без существующего внешнего или persisted-контракта.

## Логирование

- Используйте `src/shared/logger.ts`; не вызывайте `console.*` напрямую вне реализации logger.
- Передавайте структурированный payload без секретов и больших массивов данных.
- Ошибки, значимые для пользователя, показывайте через UI-состояние; лог не заменяет пользовательское сообщение.

## Тестирование

- Используйте Vitest и размещайте unit-тесты рядом с исходным модулем как `*.test.ts`.
- Покрывайте чистые расчетные модули, координатные преобразования, import/export и нормализацию состояния.
- При изменении формулы или координатного контракта обновляйте регрессионные fixture в `tests/fixtures`.
- Перед завершением изменений запускайте `npm run test`, `npm run build` и `npm run check:encoding` либо их Docker-эквиваленты.

# Architecture: Structured Modules (Vertical Slices)

## Обзор

Для проекта выбран паттерн Structured Modules с организацией по вертикальным срезам. Он подходит для инженерного браузерного инструмента, где расчетная геометрия, оборудование, баланс, визуализация и экспорт быстро станут отдельными предметными зонами, но проект пока не требует полной Explicit Architecture с жесткими портами и адаптерами.

Архитектура должна сохранить скорость разработки статического приложения, но отделить чистые расчеты от UI и рендеринга. Это особенно важно для регрессии по `formula.xlsx`, будущего Three.js-слоя и проверки ограничений размещения оборудования.

Термины: `ЦВК` относится к цилиндрической вставке корпуса и принадлежит модулю `geometry`; `ЦВ` относится к центру величины и принадлежит модулю `balance`.
## Обоснование решения

- **Тип проекта:** клиентское инженерное приложение с расчетами и интерактивной визуализацией.
- **Стек:** TypeScript, Vite, Three.js, Vitest.
- **Ключевой фактор:** расчетная предметная логика должна тестироваться отдельно от DOM, canvas и Three.js.
- **Почему не Microservices:** приложение клиентское и не требует распределенной инфраструктуры.
- **Почему не полная Explicit Architecture:** домен важен, но на текущем этапе достаточно модульных границ без тяжелой слоистой формализации.

## Правила зависимостей

- `ui` может зависеть от расчетных модулей и rendering, но расчетные модули не зависят от `ui`.
- `rendering` получает готовые модели и геометрию, но не читает DOM и не хранит бизнес-состояние.
- `geometry`, `equipment` и `balance` должны оставаться чистыми TypeScript-модулями без браузерных API.
- `persistence` преобразует данные в JSON/CSV/SVG, но не выполняет расчетные правила самостоятельно.
- Общий код допускается только в `shared`, если он нужен двум и более модулям.

## Взаимодействие модулей

- UI собирает пользовательский ввод в типизированное состояние.
- Geometry строит профиль корпуса, станции и сечения.
- Equipment проверяет размещение объектов относительно геометрии корпуса.
- Balance рассчитывает ЦТ, ЦВ, плавучесть и предупреждения.
- Rendering получает immutable snapshot состояния и отрисовывает 2D/3D-представления.
- Persistence экспортирует тот же snapshot без обращения к DOM.
- Теоретический чертеж строится в `geometry` как данные из `ProfileSnapshot`; canvas и SVG являются адаптерами этих данных и не пересчитывают формулу корпуса.

## Ключевые принципы

1. Расчеты сначала: формулы, объемы и ограничения должны быть чистыми функциями с тестами.
2. UI не владеет доменной логикой: обработчики событий только читают ввод, вызывают модули и обновляют представление.
3. Three.js — адаптер визуализации, а не источник расчетной геометрии.
4. Любое изменение формулы или координатной системы сопровождается регрессионным тестом.
5. JSON-схема проекта должна быть стабильнее UI-состояния, чтобы сохраненные файлы переживали изменения интерфейса.

## Примеры кода

### Чистая расчетная функция

```ts
export function sectionExtentsAtS(s: number, length: number, breadth: number, height: number): SectionExtents {
  const t = s / length;
  const factor = shapeFactor(t);
  return {
    radius: (height / 2) * factor,
    halfBreadthY: (breadth / 2) * factor,
    halfHeightZ: (height / 2) * factor,
  };
}
```

### UI вызывает модуль, но не содержит формулу

```ts
import { makeProfile } from "../modules/geometry/profile";
import { renderCanvasProfile } from "../modules/rendering/canvas2d";

export function updateProfileView(input: ProfileInput): void {
  const profile = makeProfile(input);
  renderCanvasProfile(document.querySelector("#profile-canvas"), profile);
}
```

## Антипаттерны

- Хранить формулы корпуса в обработчиках DOM-событий.
- Дублировать расчет радиуса в 2D, 3D и экспорте.
- Давать Three.js-сцене изменять предметное состояние напрямую.
- Смешивать проверку ограничений оборудования с отрисовкой подсветки.
- Создавать общий `utils.ts` для всего подряд без ясного владельца.

# Исправление смены shape оборудования без чтения скрытых размеров

**Дата:** 2026-07-02 07:33
**Файлы:** src/app/main.ts, src/modules/ui/equipment.ts, src/modules/ui/equipment.test.ts, src/modules/equipment/model.test.ts
**Серьезность:** medium

## Проблема

При смене формы оборудования в UI со `sphere` на `cylinder` или `box` обработчик читал размеры из еще не перерисованной строки формы. В старой строке `sphere` часть размерных inputs была скрыта и имела пустое значение. `Number("")` превращал эти значения в `0`, после чего нормализация размеров давала `Number.EPSILON` вместо дефолтных размеров новой формы.

## Причина

`readEquipmentUpdate()` всегда собирал `dimensions` для выбранного нового `shape`, не различая обычное редактирование числовых полей и событие смены формы. На событии `change` DOM еще соответствовал предыдущей форме, поэтому данные новой формы были неполными или скрытыми. `updateEquipmentItem()` уже умел использовать дефолты при смене `shape`, но UI передавал ему некорректный объект `dimensions`.

## Решение

Добавлен параметр `includeDimensions` в `readEquipmentUpdate()`. Обработчик смены `shape` в `src/app/main.ts` вызывает чтение update с `includeDimensions: false`, пишет диагностический `[FIX]` debug-log и передает update без размеров. Тогда `updateEquipmentItem()` при смене формы использует дефолтные размеры новой формы. Обычные `input`-события и изменения остальных select продолжают читать размеры как раньше.

Добавлены Vitest-тесты для UI-регрессии смены формы и прямые тесты для `equipmentVolume`, `equipmentCenter`, `equipmentDisplacedVolume`, `validateEquipmentItem`.

## Профилактика

- При смене дискриминатора формы не читать поля, которые принадлежат старому варианту UI-разметки.
- Для discriminated union updates различать изменение варианта и редактирование полей текущего варианта.
- Покрывать чистые расчетные функции прямыми unit-тестами, а UI adapters - регрессиями на неполный DOM/input state.
